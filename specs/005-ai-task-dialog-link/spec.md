### User Story 1/用户故事 1 - 对话框任务完成即收到通知 (Priority: P1)

用户在C端AI任务对话框中发起并完成一个多步骤 Agent 任务（无论成功、失败还是被中断），无需任何手动操作，已配置的飞书渠道即可在任务整体结束后短时间内收到一条任务完成通知。当前飞书发送链路已打通，缺的只是"对话框任务结束"这一事件源到通知管线的连接。

**Why this priority**: 这是本功能的直接目标。当前痛点是"飞书能发但对话框任务结束毫无动静"，先让最常见路径（有钩子或可巡检）跑通，即可交付核心价值。

**Independent Test**: 在C端AI对话框发起一个简短任务并等待其结束，观察飞书是否在约 1 分钟内收到包含任务标识与结果摘要的通知。仅实现本故事即可形成可用的最小闭环。

**Acceptance Scenarios**:

1. **Given** 飞书渠道已配置且测试发送成功，**When** 对话框中的任务正常完成，**Then** 飞书收到一条任务完成通知，包含任务标识、来源、结果状态与完成时间。
2. **Given** 同一任务已经触发过一次通知，**When** 该任务的结束事件被重复上报（例如钩子与巡检同时捕获），**Then** 仍然只发送一条通知（恰好一次，不重复）。
3. **Given** 任务以失败或被中断的方式结束，**When** 其结束事件被捕获，**Then** 通知如实反映非成功状态，而不是一律显示成功。

---

### User Story 2/用户故事 2 - 优先通过对话框任务完成钩子接入 (Priority: P2)

若目标C端AI对话框支持任务完成钩子/回调，用户只需完成一次接入配置——把对话框的任务完成钩子指向 NoticeTool 的钩子接收入口——之后每次任务结束即实时触发通知，且无需常驻轮询。

**Why this priority**: 钩子是实时性最好、资源开销最小的接入方式；只要对话框本身支持，就应作为首选路径，因此排在巡检兜底之前。

**Independent Test**: 在对话框侧配置任务完成钩子指向 NoticeTool 后运行一个任务，验证通知在任务结束数秒内送达，且此期间未启用巡检。

**Acceptance Scenarios**:

1. **Given** 对话框的任务完成钩子已指向 NoticeTool 的钩子入口，**When** 对话框任务结束，**Then** 通知在数秒内送达已配置渠道。
2. **Given** 对话框上报的钩子负载缺少部分可选字段，**When** NoticeTool 收到该事件，**Then** 通知仍能正常生成（缺失字段以默认值渲染），不因字段不全而丢弃。
3. **Given** NoticeTool 未在运行，**When** 对话框任务结束导致钩子投递失败，**Then** 对话框任务本身不受影响，且系统提供明确的接入引导说明该情况的处理方式。

---

### User Story 3/用户故事 3 - 无钩子能力时通过自动巡检兜底 (Priority: P3)

若目标对话框不提供任务完成钩子，用户可启用 NoticeTool 的自动巡检能力：通过识别对话框任务在本地的会话/状态记录，检测"进行中 → 已结束"的状态变化并触发通知。

**Why this priority**: 作为兜底路径，保证无论对话框是否提供钩子都能收到通知；实时性略差且需要能读取本地状态记录，因此优先级低于钩子路径。

**Independent Test**: 关闭钩子接入、启用自动巡检后运行一个对话框任务，验证任务结束后约一个巡检周期内收到通知。

**Acceptance Scenarios**:

1. **Given** 自动巡检已启用且目标对话框的巡检识别生效，**When** 对话框任务从进行中变为已结束，**Then** 在一个巡检周期内收到通知。
2. **Given** 巡检启动时目标任务已经结束但仍在启动补检的冷却窗口内，**Then** 启动时补发一次通知，之后不再重复发送。
3. **Given** 对话框的本地会话/状态记录损坏或暂时不可读，**When** 巡检读取失败，**Then** 跳过本轮并留下本地日志，巡检进程继续运行，已配置渠道的通知能力不受影响。
4. **Given** 对话框版本升级导致其本地记录位置或格式变化，**When** 巡检无法再识别结束状态，**Then** 用户能通过接入引导和历史记录察觉"不再产生通知"，并得到排查方向。

---

### Edge Cases/边界场景

- 任务结束事件发生在 NoticeTool 未运行期间（钩子投递失败或巡检未启动）：下次启动时如何补检、补检范围如何界定？
- 同一任务被多个触发源（钩子、巡检、MCP）先后捕获：必须保证只通知一次。
- 用户在对话框中连续完成大量短任务（如连续多轮快速问答）：如何避免通知风暴，同时不吞掉真正的完成通知？
- 对话框本地会话记录随版本升级发生变化：巡检识别失效时的表现与排查路径。
- 非对话框来源的任务结束事件（其他智能体、脚本直接调用）不应被误判为对话框任务，反之亦然；来源标识必须准确。
- 对话框任务结束但用户在对话框内删除/清理了会话记录：巡检是否还能正确判定与去重。
- MCP 兜底路径下 Agent 未主动调用通知能力（指令被忽略或上下文丢失）：系统如何呈现"该来源可能漏报"的事实，避免用户误以为已受保护。

## Requirements/需求 *(mandatory)*

### Functional Requirements/功能需求

- **FR-001**: 系统 MUST 将C端AI任务对话框的任务结束事件接入现有通知管线，使对话框任务结束能够触发已配置渠道（如飞书）的通知。
- **FR-002**: 系统 MUST 支持钩子接入路径：用户能够将对话框的任务完成钩子配置指向 NoticeTool 现有的钩子接收入口，事件负载包含任务标识、来源、结果状态、结果摘要、结束时间；可选字段缺失时以默认值渲染而非失败。
- **FR-003**: 系统 MUST 支持巡检兜底路径：提供一个针对目标对话框的巡检识别能力，通过其本地会话/状态记录检测"进行中 → 已结束"的状态迁移并触发通知；巡检的启停与间隔沿用现有巡检配置，不引入新的常驻进程。
- **FR-004**: 系统 MUST 对同一任务跨触发源（钩子、巡检、MCP）去重，保证每个任务结束恰好产生一次通知。
- **FR-005**: 对话框来源的通知 MUST 复用现有的消息模板与多渠道分发能力，无需为该来源单独重复配置渠道或模板。
- **FR-006**: 系统 MUST 在通知历史中记录对话框来源的通知及其触发方式（钩子/巡检），便于排查"为什么没收到通知"。
- **FR-007**: 巡检读取对话框本地记录失败时 MUST 跳过本轮并记录本地日志，不得导致巡检进程退出或影响已配置渠道的通知。
- **FR-008**: 系统 MUST 提供接入引导：用户无需阅读源码即可得知如何把目标对话框接入——钩子方式应指向哪个入口、巡检方式需要提供哪些信息（对话框身份、本地状态记录位置、结束判定规则）。
- **FR-009**: 事件中的来源标识 MUST 能区分"C端AI任务对话框"与其他来源（其他智能体、脚本直调），避免误判与混淆。
- **FR-010**: 现有的敏感信息过滤与防骚扰策略 MUST 同样适用于对话框来源的通知。
- **FR-011**: 本功能的目标C端AI对话框 MUST 覆盖三个产品：CodeBuddy（当前IDE中的C端AI对话框）、Claude Code 与 Codex CLI（终端中的 codex 命令）。三者均通过钩子接入（若该产品支持任务完成钩子）或巡检兜底（识别其本地会话/状态记录）接入现有通知管线；任一产品接入成功即可独立交付价值。
- **FR-012**: 系统 MUST 仅将"多步骤 Agent 任务整体结束"视为任务结束事件（含最终成功/失败/中断）；单轮简单问答 MUST NOT 触发通知。去重与通知计数的粒度与多步骤 Agent 任务一一对应。
- **FR-013**: 对既无任务完成钩子又无可读本地记录的产品，系统 MUST 允许复用现有 MCP 通知能力，由 AI Agent 在任务结束时主动上报作为兜底路径；接入引导 MUST 明确说明该路径依赖 Agent 主动调用，可靠性弱于钩子/巡检，可能漏报。

### Key Entities/关键实体 *(include if feature involves data)*

- **对话框任务事件**: 一次对话框任务的结束记录。属性：来源标识（C端AI任务对话框）、任务标识、结果状态（成功/失败/中断）、结果摘要、结束时间、触发方式（钩子/巡检）。
- **对话框巡检识别**: 描述如何识别目标对话框的任务状态。属性：对话框身份、本地会话/状态记录的位置、结束态判定规则、覆盖的会话范围。
- **接入引导信息**: 帮助用户完成一次接入配置的说明。属性：钩子入口地址/命令、所需事件字段、巡检所需配置项。
- （复用现有实体）渠道配置、消息模板、通知历史、去重记录。

## Success Criteria/成功标准 *(mandatory)*

### Measurable Outcomes/可量化结果

- **SC-001**: 对话框任务结束后，用户在 1 分钟内在已配置渠道收到通知；钩子路径下达到数秒级送达。
- **SC-002**: 连续 20 个对话框任务中，每个任务恰好收到 1 条通知，漏发率与重复率均为 0%。
- **SC-003**: 非成功结束（失败/中断）的任务，其通知状态准确率为 100%，不出现误报为成功。
- **SC-004**: 用户按接入引导从零完成接入（钩子或巡检二选一）在 10 分钟内完成，全程无需阅读源码。
- **SC-005**: 巡检兜底路径下，通知延迟不超过配置的巡检间隔加 30 秒。
- **SC-006**: 排查"未收到通知"类问题时，用户能通过通知历史在 2 分钟内确认事件是否到达以及触发方式。

## Assumptions/假设

- "C端AI任务对话框"覆盖三个已确认的产品：CodeBuddy（当前IDE中的C端AI对话框）、Claude Code 与 Codex CLI；接入方式因产品而异，按"优先钩子、巡检兜底、MCP 补充"的统一策略逐一接入。
- Claude Code 已有现成的本地会话巡检识别（历史功能），本功能重点是为 CodeBuddy 与 Codex CLI 补齐事件源，并保证三者跨触发源去重一致。
- Codex CLI 在本地留有可读取的会话记录（与 Claude Code 类似），可作为巡检识别来源；其是否提供任务完成钩子在规划阶段调研确认。
- "任务结束"仅指多步骤 Agent 任务整体结束；单轮简单问答不纳入通知范围，因此通知量以真实任务为单位，防骚扰压力可控。
- 复用 NoticeTool 现有的钩子接收入口与本机巡检调度器，不新建与之并行的触发机制。
- 飞书渠道已完成配置且测试发送成功（用户已确认的前置条件）。
- 目标对话框要么支持任务完成钩子/回调，要么在本地留有可读取的任务状态记录；两者均不可得时本功能无法生效，接入引导中需如实说明。
- Windows 桌面环境为主要运行环境（与现有部署一致）。
