# Feature Specification: Fix Task Completion Notification Content/功能规格：修复任务完成通知内容

**Feature Branch**: `009-fix-notify-content`

**Created**: 2026-11-08

**Status**: Draft

**Input**: User description: "【任务完成通知】任务 0c489af57ca84e9599e46cf2da32a945（来源 codebuddy）已结束，结果 success，结束时间 2026-11-08T04:15:47.269Z，概要为空。当前发出去的通知内容缺少固定的格式、时间不对、概要结论没有内容、任务缺少标题（用户不知道是哪一个对话任务结束了），需要解决该问题。"

## User Scenarios & Testing/用户场景与测试

### User Story 1 - Recognizable Task Title/可识别的任务标题 (Priority: P1)

作为收到任务完成通知的开发者，我希望通知里有一个明确的任务标题，让我一眼就知道是哪一个对话/任务结束了，而不是一个看不出含义的原始任务标识。

**Why this priority/优先级理由**: 这是本次反馈的核心痛点——"不知道哪个对话任务结束"。缺少标题时，通知毫无辨识度，其余内容再规范也无法让用户快速定位到具体任务。仅补上标题即可独立交付"一眼识别任务"的价值。

**Independent Test/独立测试**: 发送一条含标题的任务结束事件，验证通知首行出现该标题；再发送一条不含标题的事件，验证通知仍出现可读的兜底标题而非仅一个原始标识。

**Acceptance Scenarios/验收场景**:

1. **Given** 来源在任务结束事件中提供了标题（如对话的标题或首条用户输入摘要），**When** 系统发送通知，**Then** 通知内容以该标题作为首要识别信息，用户可据此判断是哪个任务结束。
2. **Given** 来源未提供任何标题，**When** 系统发送通知，**Then** 通知仍包含一个可读的兜底标题（如来源名称 + 简短任务标识），而非仅输出完整的不透明标识符。
3. **Given** 用户在通知中看到标题，**When** 用户浏览多个任务结束通知，**Then** 用户能区分不同任务，不产生混淆。

---

### User Story 2 - Correct and Human-Readable End Time/正确且可读的结束时间 (Priority: P1)

作为收到通知的开发者，我希望通知里的结束时间是我的本地时间、且格式清晰易读，而不是一串带时区偏移的原始 ISO 时间戳（如 `2026-11-08T04:15:47.269Z`），避免误判任务何时结束。

**Why this priority/优先级理由**: 时间错误会直接误导用户对任务进度与时效的判断，是本次反馈的明确痛点之一。仅修正时间即可独立交付价值。

**Independent Test/独立测试**: 发送一条指定结束时间的任务结束事件，验证通知中的时间已换算为用户本地时间并采用可读格式（如 `2026-11-08 12:15:47`），而非原始 UTC ISO 字符串。

**Acceptance Scenarios/验收场景**:

1. **Given** 任务结束事件包含结束时间，**When** 系统渲染通知，**Then** 时间按用户本地时区显示，且格式为 `年-月-日 时:分:秒` 这类人类可读形式。
2. **Given** 任务结束事件未提供结束时间，**When** 系统渲染通知，**Then** 使用接收时间作为结束时间，并以同样的本地可读格式显示。
3. **Given** 用户本地时区与来源时区不同，**When** 系统渲染通知，**Then** 通知始终按用户本地时区显示，不出现 UTC 偏移或来源时区的混淆值。

---

### User Story 3 - Non-Empty Result Summary/非空的概要结论 (Priority: P2)

作为收到通知的开发者，我希望"概要"字段始终有内容，即使来源没有提供概要也能看到一句有意义的结论（如成功/失败/中断），而不是留下一行空白的"概要："。

**Why this priority/优先级理由**: 空概要让通知失去结论性信息，用户无法快速判断任务结果。它建立在标题与时间已修复的基础上，作为完整性补强，可独立验证。

**Independent Test/独立测试**: 发送一条不含概要的成功任务事件，验证通知中的概要字段显示一句有意义的结论（如"任务成功完成"），而非空白。

**Acceptance Scenarios/验收场景**:

1. **Given** 任务结束事件提供了概要，**When** 系统渲染通知，**Then** 概要显示该内容（经过敏感信息过滤）。
2. **Given** 任务结束事件未提供概要且结果为 success，**When** 系统渲染通知，**Then** 概要显示一句有意义的成功结论，而非空白。
3. **Given** 任务结束事件未提供概要且结果为 failure/interrupted/unknown，**When** 系统渲染通知，**Then** 概要显示与结果状态对应的有意义的结论。
4. **Given** 概要在敏感过滤后变为空或不可用，**When** 系统渲染通知，**Then** 仍回退到基于结果状态的兜底结论，不出现空白概要。

---

### User Story 4 - Fixed and Consistent Notification Format/固定且统一的格式 (Priority: P2)

作为收到通知的开发者，我希望所有任务完成通知都遵循同一套固定的结构（标题 → 任务标识 → 结果 → 时间 → 概要），无论来源或渠道如何，内容层级稳定、字段齐全，便于快速扫读。

**Why this priority/优先级理由**: 固定格式是前三个修复的统一载体，让通知整体规范、可预期。它依赖标题、时间、概要各自就位，但作为结构约束可独立验证。

**Independent Test/独立测试**: 通过不同渠道（如飞书与邮箱）各发送一条任务结束通知，验证两则通知的结构顺序与字段一致、齐全。

**Acceptance Scenarios/验收场景**:

1. **Given** 任意来源的任务结束事件，**When** 系统渲染默认通知，**Then** 内容按固定结构排列，且标题、结果、时间、概要四个关键字段齐全、不缺失。
2. **Given** 用户启用多个渠道，**When** 同一任务结束，**Then** 各渠道收到内容结构一致的通知（仅渠道适配差异，字段与顺序不变）。
3. **Given** 用户自定义了模板，**When** 系统渲染通知，**Then** 自定义模板仍可引用标题、时间、概要等新增占位符，且缺省时使用系统提供的兜底值。

---

### Edge Cases/边界情况

- **标题为空或仅含空白/特殊字符**：系统应回退到可读兜底标题，不输出空白或杂乱首行。
- **标题或概要超长**：按既有长度上限截断或拒绝，避免撑破通知结构。
- **时间缺失或非法**：使用接收时间兜底；非法时间值按校验规则整体拒绝或回退，不输出乱码。
- **多时区/夏令时边界**：本地时区换算应稳定一致，不因时区切换产生跳变。
- **敏感信息出现在标题或概要中**（代码、密钥、路径等）：渲染前必须经敏感过滤，过滤后为空则回退到兜底结论。
- **旧版来源未携带标题字段**：通知仍能正常生成（向后兼容），并给出可读兜底标题。
- **用户自定义模板未包含新增占位符**：按模板原样渲染，新增字段仅作为可选占位符，不强制注入。

## Requirements/需求

### Functional Requirements/功能需求

- **FR-001 标题接收**: 系统必须能接收任务结束事件中的可选标题字段（来源侧提供的对话/任务标题），并将其用于通知渲染。
- **FR-002 标题兜底**: 当来源未提供标题或标题为空时，系统必须生成一个可读的兜底标题（如"来源名称 + 简短任务标识"），保证通知首行始终有可识别的任务标题，而非仅输出完整不透明标识符。
- **FR-003 标题渲染位置**: 默认通知模板必须在显要位置（首行）展示任务标题。
- **FR-004 时间本地化**: 系统必须以用户本地时区渲染任务结束时间，格式为人类可读的 `年-月-日 时:分:秒`，不得输出原始 UTC ISO 字符串。
- **FR-005 时间兜底**: 当事件未提供结束时间时，系统必须使用接收时间作为结束时间，并以同样的本地可读格式渲染。
- **FR-006 概要非空**: 通知中的概要字段必须非空；当来源未提供概要或概要经敏感过滤后为空时，系统必须基于结果状态（success/failure/interrupted/unknown）生成有意义的兜底结论。
- **FR-007 固定格式**: 默认通知必须遵循固定、一致的内容结构（标题 → 任务标识 → 结果 → 时间 → 概要），并跨所有渠道保持一致。
- **FR-008 向后兼容**: 新增标题字段必须为可选新增，旧版来源未携带该字段的事件仍必须被接受并生成合法通知（遵循宪法原则 III）。
- **FR-009 敏感过滤**: 标题与概要必须在渲染前经过敏感信息过滤，通知内容不得包含代码正文、密钥等敏感信息。
- **FR-010 模板可定制**: 通知模板仍必须支持用户自定义，标题、时间、概要等字段以占位符形式供用户引用。

### Key Entities/关键实体

- **任务结束事件/Task Completion Event**: 一次对话任务结束的标记，在原有字段（来源、任务标识、结束时间、结果、概要、触发方式）基础上新增可选的**标题**字段，作为通知的首要识别信息。
- **通知模板/Notification Template**: 通知内容的结构定义，新增**标题**占位符，并将时间、概要的渲染语义明确为"本地可读时间""非空概要"。

## Success Criteria/成功标准

### Measurable Outcomes/可度量结果

- **SC-001**: 100% 的任务完成通知都包含可识别的任务标题（无一条通知缺少标题或仅剩不透明标识符）。
- **SC-002**: 100% 的通知以用户本地时区、人类可读格式展示结束时间，无一条通知输出原始 UTC ISO 时间戳。
- **SC-003**: 0% 的通知出现空白的概要字段。
- **SC-004**: 同一任务经多渠道发送时，通知内容结构一致率达到 100%。
- **SC-005**: 试点用户中 90% 以上能在仅看通知的情况下准确识别"是哪一个任务结束"。

## Security & Data Protection/安全与数据保护

- **数据类型**: 通知内容（任务标题、结果概要、任务标识、结束时间），其中标题与概要可能包含与用户工作内容相关的上下文。
- **访问主体**: 仅本机用户本人（单用户本地工具）；通知内容仅发往用户已配置并启用的渠道。
- **授权模型**: 新增标题字段沿用既有事件校验与敏感过滤管线，最小暴露原则不变。
- **失效与撤销**: 无新增凭据；标题与概要的敏感过滤策略与既有概要一致。
- **脱敏与存储**: 标题与概要在渲染前均经敏感过滤；日志、错误信息、通知历史中不出现明文敏感信息。

## Assumptions/假设

- 结束时间"不对"的根因是当前以 UTC ISO 格式输出，未换算为用户本地时区；修复目标为"本地时区 + 人类可读格式"。
- 标题的首选来源是来源侧在任务结束事件中新增的标题字段；当来源未提供时，以"来源名称 + 简短任务标识"作为兜底标题。
- 概要为空时，按结果状态生成兜底结论（如"任务成功完成""任务失败""任务被中断""任务结束（结果未知）"）。
- 时间与概要的兜底策略不影响既有去重、重试与历史记录逻辑。
- 通知历史与模板的持久化结构按需新增字段，且均保持向后兼容（旧数据可正常读取）。
- 本次修复不改变渠道适配与通知投递链路，仅调整内容渲染语义与默认模板。
