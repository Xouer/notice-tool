# Feature Specification: Agent Task Completion Notification/功能规格：智能体任务完成通知

**Feature Branch**: `001-agent-task-notify`

**Created**: 2026-11-07

**Status**: Draft

**Input**: User description: "做一个C端的工具，用于本地AI编程智能体进行对话任务结束后场景下，工具能够收到或者监听到对话任务结束后的钩子。如果在没有钩子条件下，C端工具可以巡查对话任务状态。最终C端工具得到任务结束后的标记，自动发送消息，通过飞书，钉钉，邮箱，微信，QQ等多渠道通知给用户。来解决任务完成后，用户无法第一时间感知的问题。支持MCP协议，可以提供给其他工具调用能力，目的可以接受其他工具的钩子触发接受过来的消息。"

## User Scenarios & Testing/用户场景与测试

### User Story 1 - Configure Notification Channels/配置通知渠道 (Priority: P1)

作为使用本地 AI 编程智能体的开发者，我希望在工具中配置飞书、钉钉、邮箱、微信、QQ 等通知渠道的连接信息，并能发送一条测试消息验证连通性，以便确认"消息能够送达到我"。

**Why this priority/优先级理由**: 通知交付通路是一切价值的前提——没有可用渠道，任务结束检测就无从通知。仅"渠道配置 + 测试发送"即可独立交付价值（用户可验证消息可达性），是 MVP 的第一块拼图。

**Independent Test/独立测试**: 仅实现本故事即可通过"添加一个飞书渠道 → 点击测试发送 → 手机收到测试消息"完整验证，交付"消息可达"的独立价值。

**Acceptance Scenarios/验收场景**:

1. **Given** 用户首次使用工具，**When** 用户选择"飞书"渠道并填写机器人 Webhook 地址后保存，**Then** 该渠道出现在渠道列表中并标记为"已启用"。
2. **Given** 用户已保存至少一个渠道，**When** 用户点击"发送测试消息"，**Then** 用户在对应渠道客户端收到一条测试消息，工具界面显示发送结果（成功/失败及原因）。
3. **Given** 用户填写了无效的连接信息（如错误的 Webhook 地址），**When** 用户保存并测试，**Then** 工具给出明确的失败提示且不崩溃，提示内容不泄露任何敏感凭据。
4. **Given** 用户不再需要某渠道，**When** 用户禁用或删除该渠道，**Then** 后续任务结束通知不再发往该渠道；删除渠道时其凭据一并从本地清除。

### User Story 2 - Hook-Triggered Task Completion Notification/钩子触发任务完成通知 (Priority: P1)

作为已在智能体中注册任务结束钩子的开发者，我希望工具在收到钩子事件（即"任务结束标记"）后，自动通过我已启用的所有渠道发送完成通知，无需我守在电脑前，以便第一时间得知任务已完成。

**Why this priority/优先级理由**: 这是本工具的核心自动化价值——"任务结束 → 用户感知"链路的直达路径。与用户故事 1 共同构成最小可用产品：有渠道、有触发，即有完整闭环。

**Independent Test/独立测试**: 配置一个渠道后，向工具发送一次模拟的任务结束钩子事件，验证用户在渠道客户端收到"任务完成"通知，即可独立验证本故事。

**Acceptance Scenarios/验收场景**:

1. **Given** 用户已在本地 AI 编程智能体中注册任务结束钩子指向本工具，且至少启用了一个通知渠道，**When** 智能体的一次对话任务结束并触发钩子，**Then** 工具通过所有已启用渠道发送"任务完成"通知。
2. **Given** 钩子事件中包含任务标识与结果信息，**When** 工具收到该事件，**Then** 通知内容按用户所选模板渲染，至少包含任务标识、结束时间与任务结果概要。
3. **Given** 某个渠道发送失败，**When** 工具执行通知发送，**Then** 该渠道按策略自动重试，最终失败记入本地通知历史，且不中断其他渠道的发送。
4. **Given** 任务结束时的结果状态为失败或中断，**When** 工具发送通知，**Then** 通知中体现该结果状态，而非一律报告"完成"。

---

### User Story 3 - Task Status Polling Without Hooks/无钩子时的任务状态巡查 (Priority: P2)

作为使用的智能体不支持钩子的开发者，我希望工具能按设定的时间间隔巡查对话任务状态，在检测到任务从"进行中"变为"已结束"时自动触发通知，以便在不具备钩子条件的情况下同样获得完成提醒。

**Why this priority/优先级理由**: 巡查是钩子缺失时的兜底通路，扩大工具可覆盖的智能体范围；其价值依赖通知通路（用户故事 1）已就绪，但触发逻辑可独立开发与验证。

**Independent Test/独立测试**: 在一个可读取任务状态的智能体上开启巡查模式，运行一个对话任务至结束，验证工具检测到结束并发出通知，即可独立验证。

**Acceptance Scenarios/验收场景**:

1. **Given** 用户的智能体不支持钩子且用户已开启巡查模式，**When** 工具按用户配置的时间间隔巡查对话任务状态，**Then** 工具能识别任务从"进行中"到"已结束"的状态变化。
2. **Given** 巡查检测到某任务结束，**When** 工具触发通知流程，**Then** 通知行为与钩子触发的通知完全一致（同样的模板、渠道与去重规则）。
3. **Given** 某智能体的任务状态无法被读取，**When** 用户为其开启巡查，**Then** 工具给出明确提示"该智能体暂不支持巡查，请使用钩子或 MCP 触发"，不做静默失败。
4. **Given** 用户调整巡查间隔配置，**When** 配置保存后，**Then** 后续巡查按新间隔执行。
5. **Given** 工具运行期间同时开启钩子与巡查，**When** 两种方式先后检测到同一任务结束，**Then** 用户仅收到一轮通知（去重生效）。

---

### User Story 4 - MCP Capability for External Tools/通过 MCP 向外部工具提供能力 (Priority: P3)

作为其他工具（IDE 插件、智能体、自动化脚本等）的使用者或作者，我希望将本工具作为符合 MCP 协议标准的服务接入，调用其通知能力或把其他工具的钩子/任务结束消息转发进来触发通知，以便通知能力可被更广泛的生态复用。

**Why this priority/优先级理由**: MCP 能力把工具从"自用通知器"升级为"可被编排的通知服务"，是明确的用户要求，但价值建立在核心通知链路（故事 1、2）之上，属于生态扩展层。

**Independent Test/独立测试**: 用任一支持 MCP 协议的客户端接入本工具，发现其通知能力并发起一次调用，验证已启用渠道收到对应消息，即可独立验证。

**Acceptance Scenarios/验收场景**:

1. **Given** 本工具以 MCP 服务形式运行，**When** 外部 MCP 客户端接入并查询可用能力，**Then** 客户端能发现通知相关能力（如发送通知、上报任务结束事件）。
2. **Given** 外部工具通过 MCP 调用"发送通知"能力并传入消息内容，**When** 调用完成，**Then** 用户已启用的渠道收到对应通知，调用方收到明确的成功/失败结果。
3. **Given** 外部工具通过 MCP 上报一次任务结束事件（相当于转发其钩子消息），**When** 事件被接受，**Then** 该事件走与本地钩子一致的通知流程（相同模板、渠道与去重规则）。
4. **Given** 外部调用传入的内容不合法（如超长、格式错误或高频轰炸），**When** 工具处理该调用，**Then** 调用被拒绝并返回明确原因，不影响本地通知流程正常运行。

---

### Edge Cases/边界情况

- **钩子与巡查双通道同时命中同一任务结束**：系统必须保证"恰好一次"通知（见 FR-007），用户不会收到重复消息。
- **工具进程未运行时钩子被触发**：事件无法即时送达；工具再次启动时必须执行一次补检——通过巡查通道发现离线期间已结束的任务并补发通知（冷却窗口内去重），历史可追溯，避免长期漏通知。
- **网络故障导致所有渠道发送失败**：按重试策略处理，最终失败记入本地通知历史，用户恢复网络后可见失败记录并可手动重发。
- **渠道凭据过期或被撤销**（Webhook 失效、令牌被收回、授权码变更）：发送失败提示分类明确，引导用户更新凭据，其他渠道不受影响。
- **短时间多个任务连续/并行结束**：每个任务独立识别、独立记录，通知不互相覆盖；极端频率下按防骚扰策略聚合或限流。
- **巡查时无法读取任务状态**（智能体不支持、权限不足、状态文件被占用）：明确提示不支持的智能体，不静默失败。
- **任务结束但结果为失败/中断**：通知如实反映结果状态，避免"假完成"误导用户。
- **通知内容含敏感信息风险**（代码正文、密钥、路径等）：默认模板不包含代码正文与密钥，仅含任务标识与结果概要。
- **未配置任何已启用渠道时任务结束**：事件仍被记录于历史，用户可见"有未送达通知"的明确提示。

## Requirements/需求

### Functional Requirements/功能需求

- **FR-001 钩子接收**: 系统必须能接收本地 AI 编程智能体在对话任务结束时触发的钩子事件，并解析其中的任务标识与结束信息。
- **FR-002 状态巡查**: 在无钩子条件下，系统必须能按用户可配置的时间间隔巡查对话任务状态，识别任务结束标记。
- **FR-003 自动通知**: 在得到任务结束标记（无论来自钩子、巡查还是 MCP 上报）后，系统必须自动通过所有已启用渠道发送通知，无需人工干预。
- **FR-004 多渠道支持**: 系统必须支持飞书、钉钉、邮箱、微信、QQ 五类通知渠道，每类渠道均可独立启用与禁用。
- **FR-005 渠道配置**: 用户必须能够配置并保存各渠道所需的连接信息（如 Webhook 地址、机器人令牌、收件邮箱与授权码、推送服务密钥等），配置保存在用户本地。
- **FR-006 测试发送**: 用户必须能够对任一渠道发送测试消息，并立即看到发送结果（成功或失败原因）。
- **FR-007 恰好一次通知**: 当钩子、巡查、MCP 上报多种触发方式并存并先后命中同一任务结束时，系统必须且仅产生一轮通知。
- **FR-008 失败重试与记录**: 渠道发送失败时系统必须自动重试；最终失败必须记入本地通知历史，并给出用户可理解的失败原因分类。
- **FR-009 通知模板**: 通知内容必须支持用户自定义模板；默认模板至少包含任务标识、结束时间与任务结果概要，且不得包含代码正文、密钥等敏感内容。
- **FR-010 MCP 服务**: 系统必须以符合 MCP 协议标准的服务形式对外暴露通知能力，供其他工具发现与调用；外部上报的任务结束事件走与本地钩子一致的通知流程。
- **FR-011 通知历史**: 系统必须在本地记录通知发送历史（时间、任务标识、目标渠道、发送结果），用户可查看。
- **FR-012 凭据保护**: 渠道凭据必须以受保护方式存储于用户本地，不得出现在日志、错误信息、通知内容或导出数据中。
- **FR-013 输入校验与防滥用**: 系统必须对钩子事件与外部调用内容进行合法性校验（格式、长度、频率），并提供通知频率控制策略，防止通知轰炸。

### Key Entities/关键实体

- **通知渠道配置/Notification Channel Configuration**: 用户为某渠道（飞书/钉钉/邮箱/微信/QQ）保存的连接信息与启用状态；是通知记录的发送目标。
- **任务结束事件/Task Completion Event**: 一次对话任务结束的标记，包含来源智能体标识、任务标识、结束时间、任务结果状态（成功/失败/中断）与触发方式（钩子/巡查/MCP 上报）。
- **通知记录/Notification Record**: 一次实际发送的结果，关联某个任务结束事件与某个渠道配置，含发送状态（成功/失败/重试中）与时间戳。
- **通知模板/Notification Template**: 通知内容的结构定义，按渠道适用，用户可自定义，默认模板内置于系统。

## Success Criteria/成功标准

### Measurable Outcomes/可度量结果

- **SC-001**: 任务结束被识别后，95% 的情况下用户在 30 秒内于至少一个已启用渠道收到通知。
- **SC-002**: 凭据有效的前提下，五类渠道（飞书、钉钉、邮箱、微信、QQ）各自完成"配置 → 测试消息送达"的成功率不低于 95%。
- **SC-003**: 钩子与巡查双通道同时开启时，同一任务结束的重复通知率为 0。
- **SC-004**: 用户从安装到完成第一个渠道配置并收到测试消息，平均耗时不超过 10 分钟。
- **SC-005**: 安全审查通过——日志、错误信息、通知内容与导出数据中均不出现明文凭据（抽查零泄露）。
- **SC-006**: 外部支持 MCP 的工具可成功发现并调用通知能力，从调用到通知送达的成功率不低于 95%。
- **SC-007**: 试点用户中 90% 以上认可"任务完成后能在第一时间感知"得到解决。

## Security & Data Protection/安全与数据保护

- **数据类型**: 渠道凭据（Webhook 地址、机器人令牌、邮箱授权码、推送服务密钥）、用户标识（邮箱地址、飞书/钉钉/微信/QQ 相关标识）、通知内容（任务标识、结果概要及可能附带的路径等上下文）。
- **访问主体**: 仅本机用户本人（单用户本地工具）；外部 MCP 客户端仅能调用受限的通知触发能力。
- **授权模型**: 凭据仅存储于本地并仅用于向对应渠道发送消息；MCP 能力采用最小暴露原则——仅开放"发送通知/上报任务结束事件"等白名单操作，不提供读取凭据、读取历史明细等能力。
- **失效与撤销**: 用户可随时禁用或删除渠道，删除即同步清除其凭据；凭据在渠道侧撤销后，工具内更新或删除即可即时生效。
- **脱敏与存储**: 日志、错误信息、通知内容与导出数据中的凭据一律脱敏；凭据不经由版本库或远端同步。

## Assumptions/假设

- 目标用户为在本地运行 AI 编程智能体的个人开发者，工具以单用户本地形态运行，多租户与云端部署不在范围内。
- 各渠道连接信息由用户自行申请并持有（如飞书/钉钉机器人、邮箱授权码等）；工具不代为申请凭据。
- 微信与 QQ 没有面向个人的官方通用消息推送接口：微信默认通过第三方推送服务或企业微信机器人实现，QQ 默认通过官方机器人或第三方推送服务实现，具体服务由用户在配置时选择。
- 智能体侧钩子由用户在其智能体的配置中注册并指向本工具；若智能体不支持钩子，用户使用巡查模式或经 MCP 上报事件。
- 巡查模式覆盖常见本地智能体（可通过其本地会话日志、状态文件或本地接口读取任务状态）；对无法巡查的智能体，工具给出明确提示。
- 通知默认不包含代码正文与密钥，仅包含任务标识与结果概要。
- 通知历史仅在本地保存，默认保留 30 天，用户可随时清除。
- 用户环境具备基础网络连通性；离线导致的发送失败按重试与历史记录机制处理。
