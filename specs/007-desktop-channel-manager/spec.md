# Feature Specification/功能规格: Desktop Channel Manager/桌面渠道管理工具

**Feature Branch**: `007-desktop-channel-manager`

**Created**: 2026-11-08

**Status**: Draft

**Input**: User description: "目前项目基于命令行配置，希望增加简约风格的 C 端桌面可视化工具，支持最小化到系统托盘、开启服务、查看注册信息、注册渠道、修改渠道以及测试渠道消息发送。"

## User Scenarios & Testing/用户场景与测试

### User Story 1/用户故事 1 - View and Control the Local Service/查看并控制本地服务 (Priority: P1)

作为不熟悉命令行的个人用户，我希望在首页清楚看到通知服务是否运行，并通过明确的主要按钮启动或停止服务，以便无需记忆命令即可让通知能力开始工作。

**Why this priority/优先级理由**: 服务运行是后续接收和发送通知的前提，直观的状态与控制能直接降低首次使用门槛。

**Independent Test/独立测试**: 在没有任何渠道配置的干净环境中启动桌面工具，完成服务启动、状态查看和停止，即可独立验证核心价值。

**Acceptance Scenarios/验收场景**:

1. **Given** 服务当前未运行，**When** 用户点击“启动服务”，**Then** 界面显示启动中的过渡状态，成功后显示“运行中”，且启动操作不会重复执行。
2. **Given** 服务当前运行中，**When** 用户点击“停止服务”并确认，**Then** 服务停止，界面及时更新为“已停止”。
3. **Given** 服务因权限、配置或运行环境异常无法启动，**When** 启动失败，**Then** 界面显示“启动失败”和可执行的排查指引，不得误报为运行中。
4. **Given** 用户离开首页后再返回，**When** 首页重新展示，**Then** 服务状态与当前实际状态一致，而不是沿用过期页面状态。

---

### User Story 2/用户故事 2 - Register a Notification Channel/注册通知渠道 (Priority: P1)

作为需要接收任务通知的用户，我希望通过分步表单选择渠道类型、填写名称和所需凭据，并在保存前核对摘要，以便无需阅读命令帮助即可完成渠道注册。

**Why this priority/优先级理由**: 渠道注册是通知送达的核心配置流程，也是命令行用户转向桌面工具的主要价值。

**Independent Test/独立测试**: 从空渠道列表开始，仅使用桌面界面添加一条有效渠道，随后能在列表中看到其脱敏摘要和未启用状态。

**Acceptance Scenarios/验收场景**:

1. **Given** 用户选择一种受支持的渠道类型和连接方式，**When** 按字段提示填写完整有效的信息并确认保存，**Then** 渠道创建成功并出现在列表中，敏感值不以明文展示。
2. **Given** 表单缺少必填项、字段格式无效或同类型下名称重复，**When** 用户尝试保存，**Then** 系统定位到具体问题并阻止保存，不生成不完整渠道。
3. **Given** 已存在一条飞书或邮箱渠道，**When** 用户使用不同名称添加同类型的另一条配置，**Then** 两条配置独立存在，互不覆盖。
4. **Given** 用户已填写部分表单，**When** 用户取消并确认放弃，**Then** 不保存任何新渠道，已有渠道不受影响。
5. **Given** 新渠道保存成功但尚未测试，**When** 用户查看其状态，**Then** 状态为“未启用”，并提供下一步测试入口。

---

### User Story 3/用户故事 3 - Test Channel Delivery/测试渠道消息送达 (Priority: P1)

作为刚注册或修改过渠道的用户，我希望从渠道详情或列表发送一条测试消息，并看到明确的成功或失败结果，以便确认凭据、接收目标和网络链路确实可用。

**Why this priority/优先级理由**: “配置已保存”不等于“消息能送达”，测试反馈是用户建立信任和完成启用流程的关键。

**Independent Test/独立测试**: 使用一条已有有效渠道执行测试，在目标接收端收到可识别的测试消息，并在界面看到成功结果；再使用无效配置验证失败反馈。

**Acceptance Scenarios/验收场景**:

1. **Given** 一条未启用且配置有效的渠道，**When** 用户点击“发送测试消息”，**Then** 目标接收端收到一条标明来自 NoticeTool 的测试消息，界面显示成功并按既有规则启用该渠道。
2. **Given** 渠道凭据失效、接收目标不可达或网络不可用，**When** 测试失败，**Then** 界面显示失败及可理解的排查建议，渠道原有启用状态保持不变。
3. **Given** 一次测试仍在进行，**When** 用户再次点击同一渠道的测试按钮，**Then** 系统不重复发送，并清楚显示正在测试。
4. **Given** 存在多条渠道，**When** 用户测试其中一条，**Then** 仅目标渠道收到测试操作，其他渠道的配置和状态不受影响。

---

### User Story 4/用户故事 4 - Modify an Existing Channel/修改既有渠道 (Priority: P2)

作为需要轮换凭据或调整接收目标的用户，我希望在桌面表单中修改既有渠道，未改动的字段保持原值，以便避免删除重建和重新填写全部信息。

**Why this priority/优先级理由**: 凭据过期和接收目标变化是持续使用中的高频维护需求，部分修改能显著降低操作成本和中断风险。

**Independent Test/独立测试**: 选择一条既有渠道，仅修改名称或一项凭据，保存后确认其他字段、启用状态和历史关联均保持不变。

**Acceptance Scenarios/验收场景**:

1. **Given** 用户打开一条既有渠道的修改页面，**When** 仅修改名称或非敏感配置并保存，**Then** 修改成功，未提交的字段保留原值。
2. **Given** 修改表单中的敏感字段未填写新值，**When** 用户保存其他修改，**Then** 原敏感值继续保留且全过程不以明文回显。
3. **Given** 修改后的整体验证失败或新名称与同类型既有渠道冲突，**When** 保存被拒绝，**Then** 原渠道配置、名称和启用状态完全不变。
4. **Given** 渠道当前已启用，**When** 用户成功修改凭据或接收目标，**Then** 渠道保持原启用状态，系统不会在未请求时自动发送测试消息。
5. **Given** 渠道存在可清除的可选字段，**When** 用户显式选择清除并确认，**Then** 仅该可选字段被清除；必填字段不得以此方式置空。

---

### User Story 5/用户故事 5 - Inspect Registration Information/查看接入注册信息 (Priority: P2)

作为使用不同 AI 编程智能体的用户，我希望集中查看本机各智能体的通知接入注册信息、启停状态和最近验证结果，以便判断任务事件是否已正确接入 NoticeTool。

**Why this priority/优先级理由**: 渠道可用只是通知链路的一部分，注册信息能帮助用户区分“未接入”“已接入”和“接入失效”，减少盲目排查。

**Independent Test/独立测试**: 在至少一个智能体已注册、另一个未注册的环境中打开注册信息页，验证两者状态、来源和验证信息均准确展示，无需修改渠道。

**Acceptance Scenarios/验收场景**:

1. **Given** 本机存在受支持智能体的接入配置，**When** 用户打开“注册信息”，**Then** 能看到各智能体名称、接入状态、适用范围和最近验证结果。
2. **Given** 某智能体从未注册，**When** 查看其信息，**Then** 明确显示“未注册”，不得与“已注册但服务未运行”混淆。
3. **Given** 用户点击刷新，**When** 本机注册配置已发生变化，**Then** 页面展示最新状态，并在读取失败时说明原因。
4. **Given** 注册配置包含本机路径或用户标识，**When** 信息展示或错误呈现，**Then** 不必要的隐私信息被隐藏，且不包含任何渠道凭据。

---

### User Story 6/用户故事 6 - Keep the Tool Available in the Tray/通过托盘保持后台可用 (Priority: P2)

作为希望通知工具常驻但不占用桌面空间的用户，我希望将窗口最小化到系统托盘，并能随时恢复窗口或显式退出，以便持续运行服务而不干扰当前工作。

**Why this priority/优先级理由**: 后台常驻是桌面通知工具的基础体验，托盘能力让服务运行与窗口可见性相互独立。

**Independent Test/独立测试**: 在服务运行时将窗口最小化到托盘，确认服务状态不变，再从托盘恢复窗口；随后验证显式退出流程。

**Acceptance Scenarios/验收场景**:

1. **Given** 主窗口已打开且服务正在运行，**When** 用户最小化到托盘，**Then** 主窗口隐藏、托盘图标可见，服务继续运行且渠道配置不变。
2. **Given** 工具已最小化到托盘，**When** 用户通过托盘图标选择“打开主界面”，**Then** 原主窗口恢复并显示当前服务状态，不创建重复窗口。
3. **Given** 工具位于托盘且服务正在运行，**When** 用户选择“退出”，**Then** 系统说明退出将停止由该应用管理的本地服务并要求确认；取消退出则服务和托盘状态保持不变。
4. **Given** 服务已停止，**When** 用户最小化或恢复窗口，**Then** 不会因窗口操作隐式启动服务。

---

### Edge Cases/边界情况

- 服务在桌面工具外被启动、停止或异常退出时，界面刷新后必须反映真实状态，不能继续显示旧的“运行中”。
- 启动或停止操作尚未完成时，重复点击不得产生并发状态变更；超时后应给出明确结果和重试入口。
- 用户在桌面修改表单打开期间通过命令行改动同一渠道时，保存前必须识别版本冲突并提示重新加载，避免静默覆盖。
- 渠道配置损坏或凭据无法读取时，列表仍展示可识别的渠道条目和异常状态，不得泄露原始敏感内容。
- 测试消息外部平台长时间无响应时，用户应看到进行中状态及最终的超时结果，而不是无限等待。
- 测试成功后自动启用失败时，必须分别说明“消息已送达”和“启用未完成”，不得将两者合并为虚假的全成功。
- 系统托盘不可用或被系统限制时，窗口保持可用并提示无法托管，不得造成服务或配置不可访问。
- 没有任何渠道或注册信息时，各页面提供明确的空状态与下一步操作，不显示误导性的正常状态。

## Requirements/需求

### Functional Requirements/功能需求

- **FR-001 简约导航**: 系统 MUST 提供以左侧功能导航和右侧内容区域为主的简约桌面界面，至少包含“首页”“注册信息”“通知渠道”三个入口，并突出当前选中项与主要操作。
- **FR-002 首页概览**: 首页 MUST 集中展示服务运行状态、已配置渠道数量与启用状态摘要、注册接入状态摘要，并提供进入对应详情页的明确入口。
- **FR-003 服务控制**: 用户 MUST 能启动和停止本地通知服务；系统 MUST 展示“已停止、启动中、运行中、停止中、异常”等可区分状态，并阻止重复操作。
- **FR-004 状态真实性**: 服务状态和操作结果 MUST 来自实际状态确认；失败或状态未知时 MUST 明确提示，不得仅依据按钮点击显示成功。
- **FR-005 托盘托管**: 用户 MUST 能将主窗口最小化到系统托盘、从托盘恢复单一主窗口并显式退出；最小化和恢复 MUST NOT 改变服务运行状态。
- **FR-006 注册信息**: 系统 MUST 展示受支持智能体的名称、注册状态、适用系统、最近验证时间与结果，并允许用户主动刷新。
- **FR-007 注册状态区分**: 系统 MUST 区分“未注册”“已注册且有效”“已注册但失效”和“读取失败”，不得把注册状态与智能体进程运行状态混为一谈。
- **FR-008 渠道列表**: 系统 MUST 展示全部既有渠道的类型、名称、连接方式、启用状态和脱敏摘要，并为每条渠道提供修改和测试入口。
- **FR-009 渠道注册**: 用户 MUST 能通过桌面界面选择现有全部渠道类型及其受支持连接方式，按类型填写名称、凭据和接收目标，支持同类型多条独立配置。
- **FR-010 注册校验**: 保存新渠道前 MUST 校验必填项、字段格式、连接方式所需字段组合及同类型内名称唯一性；失败时不得创建配置。
- **FR-011 安全录入**: 敏感字段输入 MUST 默认掩码，保存前摘要 MUST 仅显示非敏感信息和脱敏标识；取消注册不得留下部分配置。
- **FR-012 新渠道状态**: 新注册渠道 MUST 沿用既有“未启用”初始状态，并提供直接测试入口；只有既有测试成功规则满足后才自动启用。
- **FR-013 部分修改**: 用户 MUST 能修改既有渠道名称、凭据、连接方式和接收目标；未提供的新值 MUST 保留，渠道类型本身不可在修改流程中变更。
- **FR-014 修改保护**: 渠道修改 MUST 在整体验证通过后一次性生效；任何失败 MUST 保留原配置、启用状态和历史关联，且不得隐式触发测试。
- **FR-015 可选字段清除**: 修改流程 MUST 将“保留敏感值”和“清除可选字段”表达为不同操作；必填字段不得被清除为空。
- **FR-016 渠道测试**: 用户 MUST 能对单一渠道发送内容固定的可识别测试消息，并看到进行中、成功、失败或超时结果；同一渠道的进行中测试 MUST 防重复提交。
- **FR-017 测试结果语义**: 测试成功 MUST 按既有规则启用目标渠道；测试失败 MUST 保留原启用状态；其他渠道不得受到影响。
- **FR-018 配置一致性**: 桌面工具与现有命令行 MUST 使用一致的渠道和注册配置；用户刷新或重新打开页面后能看到外部变更，不得形成两套互不一致的数据。
- **FR-019 操作反馈**: 所有保存、修改、测试和启停操作 MUST 提供明确结果及可执行的失败指引；错误信息不得包含明文凭据或完整敏感路径。
- **FR-020 状态持久性**: 渠道配置、启用状态及注册状态 MUST 在窗口关闭再打开和应用重启后保持准确，纯界面浏览不得修改这些状态。

### Key Entities/关键实体

- **本地服务状态/Local Service Status**: 表示本地通知服务的当前状态、最近状态变化时间和最近一次操作结果。
- **接入注册信息/Registration Information**: 表示一个受支持智能体与本工具的通知接入关系，包含适用系统、注册状态、最近验证结果和必要的非敏感配置位置摘要。
- **通知渠道/Notification Channel**: 表示一条独立的消息发送配置，包含类型、名称、连接方式、受保护凭据、接收目标和启用状态；同类型内名称唯一。
- **渠道测试结果/Channel Test Result**: 表示一次测试的目标渠道、开始与结束时间、送达结果、失败原因分类，以及是否完成自动启用，不包含明文凭据。

## Success Criteria/成功标准

### Measurable Outcomes/可度量结果

- **SC-001**: 至少 90% 的首次使用测试参与者能在 1 分钟内仅通过桌面界面确认服务状态并启动服务，无需查阅命令行帮助。
- **SC-002**: 至少 90% 的首次使用测试参与者能在 5 分钟内完成一条有效渠道的注册和测试，并在目标接收端确认收到测试消息。
- **SC-003**: 连续执行 20 次“启动、最小化到托盘、恢复、停止”后，服务与界面状态一致率为 100%，重复窗口和意外服务启停次数均为 0。
- **SC-004**: 对缺少必填项、非法字段、重名、保存失败和用户取消等场景，未授权或部分渠道配置写入的发生率为 0。
- **SC-005**: 连续执行 20 次单字段修改后，未修改字段、渠道启用状态和历史关联的保持准确率为 100%。
- **SC-006**: 在外部渠道正常响应的环境中，至少 95% 的测试操作在 30 秒内给出明确结果；异常测试均最终显示失败或超时，而非无限进行中。
- **SC-007**: 用户能在 2 分钟内通过注册信息页正确区分未注册、有效注册、失效注册和读取失败四类状态，测试判断准确率达到至少 90%。
- **SC-008**: 对界面、操作结果、错误信息和日志的安全抽查中，渠道凭据明文泄露事件数为 0。

## Security & Data Protection/安全与数据保护

- **数据类型**: 渠道名称、类型、接收目标、连接方式、访问凭据、智能体注册状态、本机配置位置摘要、服务状态和测试结果。
- **访问主体**: 仅当前本机用户可通过桌面工具查看和管理自己的配置；不提供远端管理入口、团队共享或多用户访问。
- **授权模型**: 遵循最小权限原则，仅访问本地通知服务、既有渠道配置及用户明确查看的智能体接入配置；服务启停和配置写入必须由用户主动触发。
- **输入校验**: 所有渠道名称、凭据、接收目标和连接方式组合在保存前必须校验；外部配置变更和冲突不得被静默覆盖。
- **敏感信息保护**: 凭据沿用现有本地加密保护，界面、日志、错误信息和测试结果必须脱敏；敏感表单不得预填明文，测试数据仅使用虚构信息。
- **失效与撤销**: 用户可通过修改替换失效凭据、通过停止服务暂停本地通知处理；测试失败不得自动清除凭据或改变既有启用状态。
- **传输与留存**: 测试消息仅发往用户选择的渠道和接收目标；渠道与通知历史沿用现有本地留存策略，本功能不新增远端同步。

## Assumptions & Dependencies/假设与依赖

- 首期面向 Windows 单用户桌面环境，与当前使用环境和参考图一致；macOS、Linux 桌面端及移动端不在本次范围内。
- “注册信息”指 AI 编程智能体与 NoticeTool 的本地通知接入注册信息，不是用户账号注册；本功能不包含账号、登录、付费或云同步。
