# Feature Specification: Feishu App Credential Channel/功能规格：飞书应用凭证消息通道

**Feature Branch**: `002-feishu-app-credential`

**Created**: 2026-11-07

**Status**: Draft

**Input**: User description: "目前飞书的webhook方式执行配置，实际上操作上复杂，现在采用应用app id 凭证 和 app secret的信息，来构建消息通道，是否可行，类似claw code对接的方式"

**可行性结论/Feasibility**: 可行。飞书开放平台自建应用支持以 `app_id + app_secret` 换取 `tenant_access_token`，再调用消息发送 API 主动推送消息（即 OpenClaw 类工具的对接方式）。相比群机器人 Webhook，用户无需创建群并添加自定义机器人，配置信息更简单、更稳定（Webhook 地址可能因群变更失效，而应用凭证与应用绑定）；代价是需要用户在飞书开放平台创建应用并开通消息权限，且需要提供消息接收目标（如会话 ID 或用户 ID）。

## User Scenarios & Testing/用户场景与测试

### User Story 1 - Configure Feishu Channel via App Credentials/以应用凭证配置飞书渠道 (Priority: P1)

作为使用本地 AI 编程智能体的开发者，我希望只需提供飞书自建应用的 `app_id`、`app_secret` 以及消息接收目标，就能完成飞书渠道配置并保存，而不必创建群、添加自定义机器人并复制 Webhook 地址，以降低配置门槛。

**Why this priority/优先级理由**: 应用凭证配置是本特性的核心价值——它直接替换"操作复杂"的 Webhook 配置方式，是所有后续发送能力的前提。

**Independent Test/独立测试**: 仅实现本故事即可通过"选择飞书渠道 → 填写 app_id/app_secret/接收目标 → 保存成功并出现在渠道列表"完整验证，交付"更简配置"的独立价值。

**Acceptance Scenarios/验收场景**:

1. **Given** 用户已在飞书开放平台创建自建应用并获得 `app_id` 与 `app_secret`，**When** 用户选择"飞书"渠道并填写应用凭证与消息接收目标后保存，**Then** 该渠道出现在渠道列表中并标记为"已启用"，配置过程中工具不要求填写 Webhook 地址。
2. **Given** 用户填写了缺失或格式不合法的凭证（如 `app_id` 为空、接收目标类型非法），**When** 用户保存，**Then** 工具给出明确、定位到具体字段的校验提示，且不写入任何不完整配置。
3. **Given** 用户不再需要某飞书渠道，**When** 用户删除该渠道，**Then** `app_id`、`app_secret` 与接收目标一并从本地清除，后续通知不再发往该渠道。
4. **Given** 用户已有一个按旧方式（Webhook）配置的飞书渠道，**When** 该渠道未被修改或删除，**Then** 其行为保持不变；用户也可以将飞书渠道的连接方式在"应用凭证"与"Webhook"之间切换。

### User Story 2 - Test Send via App Credential Channel/凭证通道测试发送 (Priority: P1)

作为已完成凭证配置的开发者，我希望点击"发送测试消息"后，工具自动完成凭证校验与令牌获取，并通过应用身份把测试消息送达我指定的会话，以便确认"消息能够送达到我"。

**Why this priority/优先级理由**: 令牌获取与发送链路是应用凭证方式区别于 Webhook 的关键能力；没有测试发送，用户无法验证凭证与权限是否配置正确，价值无法闭环。

**Independent Test/独立测试**: 配置好凭证后点击"测试发送"，验证指定会话收到测试消息且界面显示发送结果，即可独立验证本故事。

**Acceptance Scenarios/验收场景**:

1. **Given** 用户已保存有效的飞书应用凭证与接收目标，**When** 用户点击"发送测试消息"，**Then** 工具以应用身份获取访问令牌并发送测试消息，用户在目标会话收到消息，界面显示成功结果。
2. **Given** 用户填写的 `app_id`/`app_secret` 错误或已失效，**When** 用户测试发送，**Then** 工具提示"凭证无效或已失效"并指引检查开放平台应用设置，提示内容不包含 `app_secret` 原文。
3. **Given** 应用凭证正确但应用未开通消息发送权限，**When** 用户测试发送，**Then** 工具提示"缺少消息发送权限"并指引开通对应权限后重试。
4. **Given** 应用凭证与权限均正确但应用机器人不在目标会话中，**When** 用户测试发送，**Then** 工具提示"应用机器人不在目标会话，请将其加入会话或检查接收目标"。

### User Story 3 - Task Completion Notification via Credential Channel/凭证通道任务完成通知 (Priority: P2)

作为已注册任务结束钩子的开发者，我希望任务结束时通知通过飞书应用凭证渠道自动送达，与 Webhook 渠道行为完全一致，以便享受更简配置的同时不损失任何自动化通知能力。

**Why this priority/优先级理由**: 该故事把新通道接入既有核心通知链路（001 特性的故事 2），价值真实但建立在故事 1、2 的通道能力之上。

**Independent Test/独立测试**: 配置凭证渠道后，向工具发送一次模拟任务结束事件，验证目标会话收到"任务完成"通知，即可独立验证。

**Acceptance Scenarios/验收场景**:

1. **Given** 用户启用了飞书凭证渠道并注册了任务结束钩子，**When** 一次对话任务结束，**Then** 通知按既有模板渲染并通过该渠道送达目标会话，行为与 Webhook 渠道一致（模板、重试、去重规则相同）。
2. **Given** 任务结束时的结果状态为失败或中断，**When** 通知经凭证渠道发送，**Then** 通知如实体现该结果状态。
3. **Given** 发送过程中访问令牌恰好过期，**When** 工具执行发送，**Then** 工具自动重新获取令牌并重试，用户无需任何干预。
4. **Given** 某次发送最终失败，**When** 用户查看通知历史，**Then** 该记录包含可理解的失败原因分类，且失败不中断其他渠道的发送。

---

### Edge Cases/边界情况

- **`app_secret` 泄露风险**：凭据必须加密存储，日志、错误信息、通知内容与导出数据中一律脱敏；用户可在开放平台轮换密钥后仅更新工具内配置。
- **令牌获取失败**（网络故障、开放平台不可用）：按既有重试策略处理，最终失败记入通知历史，不静默丢弃。
- **应用未发布可用版本**：飞书自建应用需发布版本后权限才生效；工具在失败提示中包含该常见原因的指引。
- **应用被停用或凭证被吊销**：发送失败提示分类明确，引导用户更新凭证，其他渠道不受影响。
- **接收目标不存在或类型填错**（如把用户 ID 填成会话 ID）：失败提示区分"目标不存在/类型不匹配"，并说明支持的接收目标类型。
- **开放平台接口限流**：按限流响应退避重试，避免高频轰炸开放平台。
- **同一飞书租户下多个渠道配置**：每个渠道配置独立持有凭证与接收目标，互不影响。

## Requirements/需求

### Functional Requirements/功能需求

- **FR-101 凭证配置**: 系统必须支持以飞书自建应用的 `app_id`、`app_secret` 和消息接收目标（含目标类型）作为飞书渠道的连接方式，配置时不要求填写 Webhook 地址。
- **FR-102 接收目标类型**: 系统必须至少支持"会话/群"与"用户"两类接收目标，用户在配置时选择类型并填写对应标识。
- **FR-103 令牌管理**: 系统必须在发送时自动以 `app_id`/`app_secret` 获取访问令牌，并对令牌进行本地缓存与过期自动续取；不得要求用户手动维护令牌。
- **FR-104 模式共存**: 飞书渠道必须支持"应用凭证"与"Webhook"两种连接方式并存，旧 Webhook 配置保持可用；用户可在两种方式间切换。
- **FR-105 失败分类**: 发送失败时系统必须给出可理解的分类原因，至少区分：凭证无效、缺少消息权限、应用机器人不在目标会话/目标不存在、网络故障、接口限流。
- **FR-106 凭据保护**: `app_secret` 必须与其他渠道凭据同等强度加密存储，不得出现在日志、错误信息、通知内容或导出数据中；列表展示一律脱敏。
- **FR-107 校验与测试**: 保存时系统必须对凭证字段做格式与完整性校验；用户必须能对凭证渠道发送测试消息并看到成功/失败及原因。
- **FR-108 链路一致性**: 经凭证渠道发送的任务完成通知必须复用既有通知流程（模板、重试、去重、历史记录），不引入行为差异。

### Key Entities/关键实体

- **飞书凭证渠道配置/Feishu App Credential Channel**: 在既有"通知渠道配置"实体上扩展的飞书渠道连接方式，含连接模式（应用凭证/Webhook）、应用凭证（app_id、app_secret）、接收目标类型与标识。
- **访问令牌/Access Token**: 由应用凭证换取、用于调用飞书消息接口的短期令牌；仅在内存或本地受保护缓存中持有，不落盘为明文、不入库加密列之外的位置。

## Success Criteria/成功标准

### Measurable Outcomes/可度量结果

- **SC-101**: 用户从打开配置到完成"飞书凭证渠道 + 测试消息送达"，全程不涉及创建群与群机器人，平均耗时显著低于 Webhook 方式（目标 ≤ 5 分钟）。
- **SC-102**: 凭证有效且权限开通的前提下，凭证渠道"配置 → 测试发送"成功率不低于 95%。
- **SC-103**: 访问令牌过期导致的发送失败率约为 0（自动续取生效）；因令牌问题导致的最终失败记录中不出现明文凭据。
- **SC-104**: 既有 Webhook 飞书渠道在本次变更后行为零回归（现有测试全部通过）。

## Security & Data Protection/安全与数据保护

- **数据类型**: 新增应用凭证（`app_id`、`app_secret`）、接收目标标识（会话/用户 ID）；继承既有凭据保护要求。
- **访问主体**: 仅本机用户本人；凭证仅用于向飞书开放平台换取令牌并发送消息。
- **授权模型**: 遵循飞书开放平台的应用权限模型——用户自行开通"以应用身份发消息"所需权限；工具仅请求发送所需的最小权限，不读取历史消息、不订阅事件回调（无需公网回调地址）。
- **脱敏与存储**: `app_secret` 加密存储于本地，与既有凭据同机制；日志与错误信息中仅出现掩码摘要。

## Assumptions/假设

- 用户能够在飞书开放平台自行创建自建应用并开通消息发送权限（工具不代为申请）；本特性仅覆盖自建应用，商店应用不在范围内。
- 消息接收目标（会话 ID 或用户 ID）由用户在配置时提供；自动发现或枚举租户内会话/成员不在范围内。
- 接收目标为"用户"时依赖应用有向用户发消息的权限且用户在应用可用范围内；为"会话"时需应用机器人在该会话中。
- 飞书开放平台令牌接口与消息接口的现有行为（令牌有效期约 2 小时、按应用维度限流）保持稳定；令牌有效期以接口响应为准，不硬编码。
- "类似 OpenClaw 对接"指对接理念（应用凭证 + 服务端 API 主动推送），不要求复刻其具体实现细节。
