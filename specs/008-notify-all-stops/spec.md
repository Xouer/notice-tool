# Feature Specification/功能规格: Notify All Conversation Stops/所有对话停止事件均通知

**Feature Branch**: `008-notify-all-stops`

**Created**: 2026-11-08

**Status**: Draft

**Input**: User description: "单轮问答不触发，这个问题需要修改，只要当前对话停留触发stop就要发送通知消息。"

## User Scenarios & Testing/用户场景与测试 *(mandatory)*

### User Story 1/用户故事 1 - Receive Notification for Every Stop/每次停止均收到通知 (Priority: P1)

作为使用本地 AI 编程智能体的开发者，我希望当前对话无论是单轮问答还是多步骤任务，只要结束时触发 `Stop`，都能收到一轮通知，即使对话窗口仍保持打开，也不必继续守在电脑前确认结果。

**Why this priority/优先级理由**: 单轮问答被现有规则排除，直接导致用户无法感知对话已经结束，是本次必须修复的核心问题。仅实现本故事即可恢复“对话停止即提醒”的完整价值。

**Independent Test/独立测试**: 配置并启用一个可用通知渠道，在同一对话中分别完成一次单轮问答和一次多步骤任务，保持对话窗口打开，验证两次 `Stop` 均各自产生一轮通知。

**Acceptance Scenarios/验收场景**:

1. **Given** 当前对话已接入 `Stop` 通知且至少一个通知渠道已启用，**When** 一次单轮问答结束并触发 `Stop`，**Then** 系统发送一轮通知，不因内容是简单问答而忽略事件。
2. **Given** 当前对话已接入 `Stop` 通知，**When** 一次多步骤任务成功、失败或被中断并触发 `Stop`，**Then** 系统仍按现有行为发送一轮通知，并如实呈现可获得的结果状态。
3. **Given** 对话结束后窗口仍停留在当前会话且用户未关闭或切换会话，**When** 系统收到该次 `Stop`，**Then** 通知照常发送，不以窗口关闭、会话切换或任务复杂度作为附加条件。
4. **Given** 当前对话仅保持打开但未触发 `Stop`，**When** 用户查看通知结果，**Then** 系统不会仅因窗口停留或回答看似结束而自行生成通知。

---

### User Story 2/用户故事 2 - Distinguish New Stops from Duplicate Reports/区分新停止与重复上报 (Priority: P2)

作为在同一对话中连续提问的开发者，我希望每一次新的 `Stop` 都能独立通知，同时同一个 `Stop` 被重复上报时不会收到重复消息，以便通知数量与真实结束次数一致。

**Why this priority/优先级理由**: 放开单轮问答后，如果仍按整个对话或任务生命周期去重，后续问答会继续漏报；如果完全不去重，又会造成重复提醒。本故事确保修复不会引入新的通知准确性问题。

**Independent Test/独立测试**: 在同一对话中连续触发两次不同的 `Stop`，确认产生两轮通知；再将其中一次相同事件重复上报，确认不会增加通知轮次。

**Acceptance Scenarios/验收场景**:

1. **Given** 同一对话已经完成一次单轮问答并发送过通知，**When** 用户继续提问并产生一次新的 `Stop`，**Then** 系统再次发送一轮通知，不因对话标识相同而抑制。
2. **Given** 系统已经处理过某个 `Stop`，**When** 同一个事件因重复投递或多触发源再次到达，**Then** 系统沿用既有去重能力，仅保留一轮通知。
3. **Given** 某个 `Stop` 缺少可选的任务摘要或结果字段，**When** 系统处理该事件，**Then** 仍发送通知并使用既有默认展示，不因可选信息缺失而丢弃事件。
4. **Given** 某次通知发送失败，**When** 系统按既有策略重试或记录结果，**Then** 该次 `Stop` 的处理状态可在通知历史中追溯，且不被错误记为已成功送达。

---

### Edge Cases/边界场景

- 同一对话连续进行多轮简单问答，每轮均触发不同的 `Stop`：每轮都应独立通知，不能只在第一轮或最后一轮通知。
- 同一个 `Stop` 被钩子重复投递，或被多个既有触发源同时捕获：只产生一轮通知。
- `Stop` 到达时对话窗口仍打开、已最小化或已失去焦点：这些界面状态不影响通知。
- `Stop` 到达但没有可用的任务标识、结果摘要或明确成功状态：使用现有默认值和来源信息生成通知，不得静默丢弃。
- 没有已启用渠道、渠道凭据失效或网络不可用：事件及失败结果仍按现有规则记录和重试，不得显示为已成功送达。
- 高频产生多个不同的 `Stop`：每个事件均进入通知流程，不得重新引入“单轮问答不通知”或“每个对话只通知一次”的隐式过滤。
- 用户停用了相关钩子模板或通知渠道：后续通知按既有启停规则停止，但既有历史记录仍可查看。
- 通知内容可能包含对话标识或结果摘要：继续沿用既有敏感信息过滤与脱敏要求，不扩大默认采集范围。

## Requirements/需求 *(mandatory)*

### Functional Requirements/功能需求

- **FR-001 全量停止通知**: 系统 MUST 将通过现有入口接收且通过既有合法性校验的每一个 `Stop` 事件送入通知流程，无论其对应单轮问答还是多步骤任务。
- **FR-002 取消复杂度过滤**: 系统 MUST NOT 以“单轮简单问答”“非 Agent 任务”或任务步骤数量为由抑制 `Stop` 通知；既有同类排除规则 MUST 被移除或调整为不再影响本场景。
- **FR-003 窗口状态无关**: 系统 MUST 在对话仍停留于当前会话时正常处理 `Stop`，不得要求用户关闭、切换或清理对话后才通知。
- **FR-004 新事件独立处理**: 同一对话或同一任务上下文中的每一个不同 `Stop` MUST 作为独立通知机会处理，不得按整个对话或任务生命周期只通知一次。
- **FR-005 重复事件去重**: 系统 MUST 沿用并适配既有去重规则，使同一个 `Stop` 的重复投递或跨触发源重复上报只产生一轮通知，同时不得误合并不同的 `Stop`。
- **FR-006 复用通知能力**: `Stop` 通知 MUST 复用现有消息模板、全部已启用渠道、失败重试和通知历史能力，不要求用户为单轮问答重新配置渠道或模板。
- **FR-007 可选信息降级**: 当 `Stop` 缺少可选的任务标识、结果摘要或状态信息时，系统 MUST 使用现有默认展示并继续通知；缺少可选信息不得成为漏报原因。
- **FR-008 无事件不合成**: 系统 MUST 仅在实际收到或识别到 `Stop` 时触发本功能，不得仅根据对话窗口停留、长时间无操作或回答内容看似完成而合成结束事件。
- **FR-009 历史可追溯**: 系统 MUST 在通知历史中保留已接收的单轮与多步骤 `Stop` 的去重、发送成功或失败结果，并结合接入状态与事件记录，使用户能够区分事件未到达、事件被去重和渠道发送失败。
- **FR-010 文档口径一致**: 面向用户的接入说明、默认模板说明和相关功能描述 MUST 明确“单轮问答与多步骤任务只要触发 `Stop` 均通知”，不得继续宣称单轮问答默认不触发。
- **FR-011 既有能力兼容**: 本次行为变更 MUST NOT 改变渠道配置、消息模板、通知历史、凭据保护及用户既有启停设置的既有含义和使用方式。
- **FR-012 安全策略延续**: 单轮问答通知 MUST 继续遵守现有输入校验、敏感信息过滤、日志脱敏和本地数据保护规则。

### Key Entities/关键实体

- **对话停止事件/Conversation Stop Event**: 一次对话结束时产生的 `Stop`，包含来源、可获得的对话或任务标识、结束时间、可获得的结果状态与摘要，以及用于识别重复上报的事件特征。单轮或多步骤只是事件背景，不再决定是否有资格通知。
- **通知轮次/Notification Round**: 一个不同 `Stop` 对应的一轮通知处理，按现有规则投递到全部已启用渠道，并记录去重及各渠道发送结果；不同 `Stop` 对应不同通知轮次。
- **通知记录/Notification Record**: 复用既有实体，关联对话停止事件、通知轮次、目标渠道、处理状态和时间，用于追踪漏报、重复与发送失败。

## Success Criteria/成功标准 *(mandatory)*

### Measurable Outcomes/可量化结果

- **SC-001 单轮覆盖**: 在通知接入和渠道均可用时，连续完成 20 次均触发 `Stop` 的单轮问答，20 次均各自产生一轮通知，漏发率为 0%。
- **SC-002 既有场景回归**: 在相同条件下，连续完成 20 个均触发 `Stop` 的多步骤任务，成功、失败和中断场景的通知触发率均为 100%，结果状态展示准确率为 100%（事件提供状态时）。
- **SC-003 连续对话准确性**: 在同一保持打开的对话中连续触发 10 个不同 `Stop`，恰好产生 10 轮通知，不因对话标识相同而漏发。
- **SC-004 去重准确性**: 对同一 `Stop` 重复上报 10 次，最终仅产生 1 轮通知；不同事件的重复通知率与错误合并率均为 0%。
- **SC-005 通知及时性**: 在通知接入、工具和渠道均可用时，至少 95% 的 `Stop` 在事件到达后 30 秒内送达至少一个已启用渠道。
- **SC-006 排查效率**: 用户能在 2 分钟内结合接入状态、事件记录与通知历史，判断一次单轮问答的 `Stop` 是未到达、已去重、发送成功还是发送失败。
- **SC-007 文档一致性**: 所有面向用户且描述触发范围的相关说明均完成口径检查，遗留“单轮问答不触发通知”的现行说明数量为 0。
- **SC-008 安全保持**: 安全抽查中，本次新增或变更的通知记录、日志和错误信息泄露凭据或新增对话正文的事件数为 0。

## Scope & Compatibility/范围与兼容性

- 本次包含：已接入对话的 `Stop` 通知判定调整、连续事件与重复事件的准确区分、通知历史追溯，以及相关用户说明的统一更新。
- 本次不包含：为没有 `Stop` 的产品合成结束事件、新增通知渠道、新增消息模板、新增按任务复杂度过滤的开关，或重新定义巡检及其他既有来源的独立触发语义。
- 本次明确取代既有规格和说明中的“单轮简单问答不触发通知”规则；多步骤任务结束通知、跨触发源去重、失败重试、渠道启停和模板启停等其他既有行为保持不变。
- 既有用户的渠道、模板和钩子启停状态继续有效；行为更新后，已启用接入产生的单轮 `Stop` 默认纳入通知，无需用户重新接入。

## Security & Data Protection/安全与数据保护

- **数据类型**: 沿用现有 `Stop` 事件元数据、对话或任务标识、结果摘要、通知记录和渠道信息；本次不默认采集对话正文、代码正文或新增敏感字段。
- **访问主体**: 仅当前本机用户可查看本地通知历史和管理接入；通知内容仅发送至用户已启用的渠道。
- **授权模型**: 沿用现有最小权限与用户显式启停机制，不因取消单轮过滤而扩大外部调用方可访问的能力或数据范围。
- **输入校验**: 所有 `Stop` 仍须通过现有格式、长度与合法性校验；无效事件的拒绝不得被误记为有效事件已通知。
- **敏感信息保护**: 通知、日志、错误信息和测试示例继续过滤凭据、密钥及不必要的个人内容；结果摘要沿用既有脱敏与默认展示规则。
- **失效与撤销**: 用户可通过现有渠道或钩子模板的停用机制停止后续通知；停用不删除既有历史，历史留存与清除沿用现有策略。

## Assumptions/假设

- “当前对话停留触发 `Stop`”是指对话仍保持打开时，智能体已经实际发出 `Stop`；窗口是否关闭不作为通知条件。
- 单轮问答现在属于明确需要通知的范围，这是对既有产品规则的有意变更，而不是新增可选的实验行为。
- 一轮通知指同一 `Stop` 按现有规则投递到全部已启用渠道，并不表示只选择一个渠道发送。
- 用户已完成现有智能体接入，且至少配置了一个通知渠道；渠道不可用时的重试与失败记录不属于本次新增能力。
- 现有事件能够提供足以区分不同 `Stop` 或识别重复上报的信息；若个别来源信息不足，规划阶段需在不恢复单轮过滤的前提下确定兼容的区分口径。
- 巡检及其他既有来源继续遵守原有触发语义；本次只强制要求实际 `Stop` 不再被单轮问答规则拦截，并确保共享去重不会误合并不同事件。
