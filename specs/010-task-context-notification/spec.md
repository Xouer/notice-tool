# Feature Specification: Task Context Notification/任务上下文通知

**Feature Branch**: `010-task-context-notification`

**Created**: 2026-11-08

**Status**: Draft

**Input**: User description: "任务完成通知里，标题是 codebuddy · 97645996，概要只写'任务成功完成'，我无法知道具体是哪个任务完成，体验很难受，需要一个好的解决方案。"

## User Scenarios & Testing/用户场景与测试 *(mandatory)*

### User Story 1 - Readable Task Title in Notification/通知中的可读任务标题 (Priority: P1)

用户在 AI 编程助手中发起一个多步骤任务（例如"帮我修复登录超时的问题"）。任务结束后，用户收到完成通知，希望**一眼就能认出这是哪一个任务**，而不是看到一串无意义的技术标识。

当前通知标题显示为 `codebuddy · 97645996`（来源名 + 任务 ID 前 6 位），用户无法据此判断任务内容，必须打开对话历史逐条比对，体验很差。

**Why this priority**: 这是本特性的核心价值——通知的首要作用就是让用户"知道发生了什么"，而任务身份识别是其中最基础、最常用的诉求。解决了它，其余改进才有意义。

**Independent Test**: 发起一个带有明确主题的任务，等待结束并观察通知：通知首行应出现该任务的可读主题（如"修复登录超时问题"或用户首条请求的摘要），而非仅技术标识。仅实现本故事即可独立交付价值。

**Acceptance Scenarios**:

1. **Given** 一个任务在结束时其主题/标题可被获取，**When** 任务结束触发完成通知，**Then** 通知首行展示该任务的可读主题，而非仅显示任务 ID 前缀。
2. **Given** 一个任务的主题/标题不可获取，但可获取到用户的首条真实请求，**When** 任务结束触发完成通知，**Then** 通知首行以用户首条请求的摘要作为任务身份信息。
3. **Given** 任何可读上下文都无法获取，**When** 任务结束触发完成通知，**Then** 通知仍能发出，并以技术标识兜底，同时明确提示该通知无法识别具体任务（降级可见）。

---

### User Story 2 - Meaningful Task Summary/有意义的任务概要 (Priority: P2)

用户收到通知后，除了想知道"是哪个任务"，还希望概要能**反映任务实际做了什么或达成了什么**，而不是一句泛泛的"任务成功完成"。

**Why this priority**: 在任务身份可识别的基础上，进一步让概要承载实质信息，能显著减少用户点开对话确认的次数；但相对于"能认出任务"而言是次要增强。

**Independent Test**: 对一个内容明确的任务（如"给订单接口补充参数校验"），观察通知概要：概要应优先体现任务最终结论（如"已完成校验并更新 3 个文件"），结论缺失时体现任务目标，而非仅显示结果状态词。

**Acceptance Scenarios**:

1. **Given** 任务结束后可获取到任务结论（如最后一条完整回复），**When** 生成完成通知，**Then** 通知概要优先展示任务结论的摘要。
2. **Given** 任务结论不可获取、但存在可获取的内容/目标描述，**When** 生成完成通知，**Then** 通知概要展示任务内容或目标的摘要，而非仅展示结果状态。
3. **Given** 任务结论与内容/目标描述均不可获取，**When** 生成完成通知，**Then** 概要回退到结果状态描述，但不应掩盖"无法识别任务"这一事实。

---

### User Story 3 - Distinguish Consecutive Tasks/连续任务可区分 (Priority: P3)

用户在同一会话内连续发起多个任务（或同时开着多个会话），每个任务结束时收到的通知必须**能相互区分**，不能被误认为是同一条。

**Why this priority**: 当任务身份信息被引入后，必须保证不同任务（即使同一会话、同一结果状态）在通知中具备可区分的身份，否则会引入"张冠李戴"的新困扰；属于对 P1 的正确性保障。

**Independent Test**: 在同一会话内连续完成两个不同主题的任务，观察两条通知：两条通知的任务身份信息应不同、可区分。

**Acceptance Scenarios**:

1. **Given** 同一会话内先后完成两个不同任务，**When** 各自触发完成通知，**Then** 两条通知携带不同的任务身份信息，用户可区分。
2. **Given** 多个会话并发完成，**When** 各自触发完成通知，**Then** 各通知的身份信息能定位到对应会话与任务。

---

### Edge Cases/边界情况

- 来源侧未提供任何标题、摘要或转录路径时，通知如何处理？（应仍发出并降级为技术标识，同时可见提示降级）
- 任务标题/用户请求过长时如何展示？（应截断到合理长度且不破坏可读性）
- 任务身份信息中夹带敏感内容（密钥、凭据、内部路径）时如何处理？（应过滤脱敏，不泄露）
- 转录文件不存在、不可读或格式异常时如何处理？（应跳过并尝试其他上下文来源）
- 首条"用户消息"实际是系统注入或命令时如何处理？（应跳过，改取下一条真实用户消息）
- 任务结论不可获取（任务被中断、最后一条回复为"Interrupted by user"）时如何处理？（应跳过该结论并降级到首条用户消息或结果状态）
- 结论仅存在于 AI 思考过程而非可见回复时如何处理？（只取可见回复文本，不采集思考过程）

## Requirements/需求 *(mandatory)*

### Functional Requirements/功能需求

- **FR-001**: 系统 MUST 在任务完成通知中携带可唯一识别该任务的可读信息（任务主题/标题或用户请求摘要），而非仅技术标识。
- **FR-002**: 系统 MUST 在任务存在可读标题/主题时，优先使用该标题作为通知的首要身份标识。
- **FR-003**: 系统 MUST 在任务无标题时，从可用上下文（用户首条真实请求、任务目标）提取有意义的任务描述。
- **FR-004**: 系统 MUST 使通知概要体现任务的实际内容、目标或最终结论，而非仅展示结果状态；其中任务结论（若可得）应作为概要的优先来源。
- **FR-005**: 系统 MUST 仅在无法获取任何可读上下文时，才回退到技术标识（如任务 ID），且此时通知仍须成功发出。
- **FR-006**: 系统 MUST 对任务身份信息与概要做长度截断，使其符合各通知渠道的长度限制。
- **FR-007**: 系统 MUST 对任务身份信息与概要执行敏感信息过滤，确保不泄露凭据、密钥或完整对话内容。
- **FR-008**: 系统 MUST 保证同一会话内的连续任务、以及不同会话的任务，在通知中具备可区分的身份信息。

### Key Entities/关键实体 *(include if feature involves data)*

- **Task Completion Event/任务完成事件**: 任务的来源、唯一任务标识、可读标题、内容概要、结果状态、结束时间。
- **Task Context/任务上下文**: 用于识别任务的业务信息——对话主题/标题、用户首条请求、任务目标摘要、任务最终结论。
- **Notification Content/通知内容**: 由任务上下文渲染出的标题与正文，是面向用户的可读载体。

## Success Criteria/成功标准 *(mandatory)*

### Measurable Outcomes/可衡量结果

- **SC-001**: 至少 90% 的任务完成通知携带可读的任务身份信息（标题或用户请求摘要），而非仅技术标识。
- **SC-002**: 用户收到通知后，无需打开原对话即可准确判断"是哪一个任务"。
- **SC-003**: 同一会话内的连续任务在通知中可被区分，不出现两个不同任务使用完全相同的身份描述。
- **SC-004**: 通知内容不超过各渠道长度限制，且敏感信息零泄露。

## Assumptions/假设

- 来源侧（CodeBuddy / Claude Code / Codex）在任务结束事件中会提供任务上下文（标题、摘要或转录文件）；若来源侧未提供，则从本地转录文件中提取。
- 任务结论从本地转录的最后一条完整 AI 回复中提取；仅当任务正常完成且回复未被中断时可得，否则降级到首条用户消息或结果状态。
- 所有通知渠道统一采用改进后的任务可识别内容。
- 标题与概要的长度限制沿用现有约定（标题较短、概要稍长），具体上限在计划阶段确定。
- 敏感信息过滤沿用现有机制，并扩展到任务身份信息与概要。
