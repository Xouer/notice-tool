# Feature Specification: Channel Config Update & Multi-Config/渠道配置修改与同类型多条配置

**Feature Branch**: `004-channel-update-multi`

**Created**: 2026-11-07

**Status**: Draft

**Input**: User description: "1.目前使用无法进行修改配置情况，需要增加修改配置的能力。2.要具备可以添加相同类型多条的配置。"

## Clarifications/澄清

### Session 2026-11-07

- Q: 第 2 条需求"可以条件相同类型多条的配置"的具体含义？→ A: **同类型多条独立配置**——同一渠道类型添加多条独立配置，以名称区分；所有已启用渠道都会收到通知；不涉及按条件路由，也不涉及主备切换。
- Q: 修改已启用渠道的凭据后，启用状态如何处理？→ A: **保持启用**（FR-007 现状），由用户自行 `test` 验证；update 不引入隐式网络调用，不自动禁用、不自动 test。
- Q: 部分更新语义下如何清除可选字段（如钉钉加签密钥、SMTP 用户名）？→ A: **标志传空值清除**——如 `--secret ""` 显式置空即清除该可选字段；未提供的字段仍保留原值。

## User Scenarios & Testing/用户场景与测试 *(mandatory)*

### User Story 1 - Update Existing Channel Credentials & Name/修改既有渠道的凭据与名称 (Priority: P1)

用户已通过 `notice channel add` 添加了一条通知渠道（例如飞书应用凭证），之后凭据发生变更（如更换了 App Secret、换了接收群、更换 SMTP 授权码）或想修正渠道名称。当前只能先 `remove` 再 `add`，操作繁琐且丢失该渠道原有的启用状态与历史关联。用户希望直接对既有渠道执行修改：通过命令行标志更新部分凭据字段（未提供的字段保持不变），或改名，且修改后可立即用 `test` 验证。

**Why this priority**: 凭据轮换（密钥过期、授权码重置）是日常运维的必然场景，无法修改意味着每次变更都要删除重建并重新测试，是当前使用中最直接的痛点。

**Independent Test**: 添加一条飞书渠道后，仅传入新的 `--app-secret` 执行修改命令，其余字段不变；`list` 显示新摘要、`test` 成功送达、原启用状态保留。

**Acceptance Scenarios**:

1. **Given** 已存在名为 `my-feishu` 的未启用飞书渠道，**When** 执行修改并仅提供新的 App Secret 标志，**Then** 该渠道仅凭据中 App Secret 被更新，其余字段（类型、接收目标等）保持不变，凭据以新密文重新加密入库。
2. **Given** 已存在名为 `old-name` 的已启用渠道，**When** 执行改名操作将其改名为 `new-name`，**Then** 渠道启用状态保持为已启用，且不再存在 `old-name`。
3. **Given** 修改时提供了不完整的凭据组合（如飞书 app 模式缺少 receive-id），**When** 执行修改，**Then** 系统报错并明确指出缺失/非法的字段，原配置保持不变。
4. **Given** 指定的渠道名称不存在，**When** 执行修改，**Then** 返回明确错误（退出码 2）并提示使用 `notice channel list` 查看。
5. **Given** 用户在修改模式下将渠道类型相关的凭据从一种连接方式改为另一种（如飞书从 app 模式改为 webhook 模式），**When** 提供了新方式所需的完整标志，**Then** 凭据整体按新方式校验并替换。

---

### User Story 2 - Multiple Configs of Same Type/同类型渠道的多条配置 (Priority: P2)

用户需要为同一渠道类型维护多条配置，例如：飞书应用凭证同时发往"项目群"和"个人"，或配置两个不同的邮箱收件地址。用户希望可以用不同名称为同一类型添加多条配置，各条配置独立管理（独立启用/禁用、独立测试、独立修改、独立删除），并在发送时都能正常工作。

**Why this priority**: 这是多项目/多接收方用户的核心诉求；当前数据模型（type+name 唯一）虽已具备存储基础，但用户在实际使用中遇到"同名渠道已存在"报错后无法直观理解如何配置多条，且需要在规格中明确各流程（列表、测试、发送分发）对同类型多条配置的行为。

**Independent Test**: 添加两条同类型（如 email）不同名称的渠道，分别 `test` 均可成功，`list` 展示两条独立记录，禁用其中一条不影响另一条发送。

**Acceptance Scenarios**:

1. **Given** 已存在名为 `feishu-a` 的飞书渠道，**When** 添加另一条类型同为 feishu、名称为 `feishu-b`、接收目标不同的渠道，**Then** 添加成功，两条渠道独立存在。
2. **Given** 存在同类型的多条渠道且均已启用，**When** 触发一次任务完成通知，**Then** 每条启用的渠道均按其自身配置发送。
3. **Given** 存在同名渠道（无论类型是否相同），**When** 再次添加同名渠道，**Then** 报错"同名渠道已存在"并给出清晰指引（改名或先删除）。
4. **Given** 对多条同类型渠道中的一条执行 `enable/disable/remove/test`，**When** 操作完成，**Then** 仅该条受影响，其余同类型渠道不受影响。

### User Story 3 - Interactive Update Wizard/交互式向导修改配置 (Priority: P3)

偏好交互式操作的用户（以及已通过 `channel add` 向导完成配置的用户）希望在交互终端运行修改命令时，同样进入分步向导：先选择要修改的渠道，再选择修改范围（仅凭据 / 仅名称 / 全部），向导预填当前值，逐项确认后保存；保存前展示摘要，敏感值保持掩码/不回显。

**Why this priority**: 与既有 add 向导体验保持一致，降低非脚本用户的出错概率；依赖 US1 的底层修改能力，故排后。

**Independent Test**: 在交互终端运行 `notice channel update <name>`（不带凭据标志），向导启动并预填当前配置；取消修改则原配置不变。

**Acceptance Scenarios**:

1. **Given** 交互终端中已存在渠道 `my-feishu`，**When** 运行修改命令且未提供任何凭据标志，**Then** 进入向导，当前凭据以掩码形式预填展示，可逐项修改或跳过。
2. **Given** 向导中用户修改了部分字段，**When** 选择保存，**Then** 显示修改摘要（敏感值掩码），确认后写入；选择取消则不做任何更改。
3. **Given** 非交互环境（无 TTY）运行修改命令且凭据标志不完整，**When** 命令执行，**Then** 退出码 2 并指引使用命令行标志方式；`--json` 模式不弹出向导。

---

### Edge Cases/边界情况

- 修改时新旧名称冲突（改名成一个已存在的名称）→ 报错"同名渠道已存在"，不覆盖既有渠道。
- 修改过程中校验失败 → 原凭据密文与原配置保持不变（原子性）。
- 对已删除的渠道执行修改 → 报"未找到渠道"（退出码 2）。
- 同类型多条渠道中某一条发送失败 → 不影响其他同类型渠道的发送与各自的重试/状态记录。
- 修改未启用渠道的凭据 → 保持未启用状态，仍需 `test` 成功后自动启用。
- 清除必填字段（如 `--to ""`）→ 视为非法值，归一化校验报错定位到该字段，原配置不变；仅可选字段允许空值清除。
- 向导中可选字段的清除：沿用空输入=保留的导航语义，显式选择"清除该字段"（可选字段提供清除选项，必填字段不提供）。
- `--json` 模式下的修改输出 → 纯 JSON（stdout），包含更新后的名称/类型/启用状态与掩码摘要。

## Requirements/需求 *(mandatory)*

### Functional Requirements/功能需求

- **FR-001**: 系统 MUST 提供 `notice channel update <name>` 子命令，允许用户修改既有渠道的凭据字段与名称。
- **FR-002**: 修改凭据时，系统 MUST 支持部分更新语义：未在命令行中提供的字段保留原值，提供的字段经整体校验后替换；对可选字段，显式传空值（如 `--secret ""`）表示**清除**该字段（2026-11-07 澄清）。
- **FR-003**: 系统 MUST 支持通过修改操作变更渠道的连接方式（如飞书 app ↔ webhook），变更后按新方式的规则整体校验凭据。
- **FR-004**: 系统 MUST 支持通过修改操作重命名渠道；改名后同名唯一约束（同 type 内）仍须满足。
- **FR-005**: 所有修改 MUST 在写入前通过既有凭据校验（`validateChannelInput` 等价校验）；校验失败时原配置 MUST 保持不变。
- **FR-006**: 修改成功后凭据 MUST 以新密文重新加密入库；列表、错误信息与导出中一律掩码，不泄露明文。
- **FR-007**: 修改操作 MUST 保留渠道的启用状态与关联的历史通知记录。
- **FR-008**: 交互终端运行修改命令且未提供凭据标志时 MUST 进入交互式向导，预填当前配置（敏感值掩码）；`--json` 与非 TTY 环境 MUST 拒绝向导并指引标志方式（与 add 行为一致）。
- **FR-009**: 系统 MUST 允许同一渠道类型存在多条配置，各条以名称区分；同 type 内名称唯一，不同 type 之间名称可重复。
- **FR-010**: 同类型的每条配置 MUST 可独立执行启用/禁用/测试/修改/删除，互不影响。
- **FR-011**: 通知分发时系统 MUST 对每条启用的渠道（含同类型多条）按其自身配置独立发送并独立记录结果。
- **FR-012**: 添加同名渠道（同 type 内）时系统 MUST 报错并给出可操作的指引；向导路径 MUST 提供改名/覆盖/取消选择（沿用 add 现有交互）。

### Key Entities/关键实体 *(include if feature involves data)*

- **通知渠道（notification_channels）**: 现有实体，属性含 type、name、credentialsBlob（密文）、enabled。约束：`(type, name)` 唯一 —— 这是"同类型多条配置"的数据基础，本特性不改变该约束。修改操作更新 credentialsBlob（重新加密）与 name。
- **通知记录（notification_records）**: 现有实体，通过 channel_id 关联渠道；渠道修改（含改名、改凭据）不影响历史记录关联，仅渠道删除时置空。

## Success Criteria/成功标准 *(mandatory)*

### Measurable Outcomes/可度量结果

- **SC-001**: 用户完成一次凭据轮换（修改 App Secret / SMTP 授权码）可在一条命令内完成，无需删除重建。
- **SC-002**: 修改后未通过校验时，原配置 100% 保持可用（无半写状态）。
- **SC-003**: 用户可为同一类型创建任意多条（≥2 条）不同名称的配置，且每条均能独立完成 test → 启用 → 收到通知的完整流程。
- **SC-004**: 修改与多条配置的凭据在 list 输出、日志与 `--json` 结果中 100% 掩码显示。

## Assumptions/假设

- 第 2 条需求已于 2026-11-07 澄清确认为"同类型多条独立配置"：同一渠道类型下用不同名称区分多条凭据/接收目标，所有已启用渠道均收到通知；**不涉及**按条件（如消息内容、任务结果）路由，**不涉及**主备切换。
- 修改能力沿用现有 add 的命令行标志集合与校验规则，不引入新的凭据字段。
- 交互式向导复用既有 add 向导的步骤结构与 IO 抽象，增加"选择渠道 → 选择修改范围"两步。
- 不涉及修改渠道类型本身（如 email 改为 feishu）；如需换类型，建议删除后重新添加。
- 数据库 schema 无需迁移（唯一约束与实体结构不变），改动集中在 CLI 命令层、向导与仓储更新方法。
