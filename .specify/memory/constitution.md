# NoticeTool Constitution

## Core Principles

### I. 简单设计
<!-- YAGNI -->
实现必须从最简单的可行方案出发；杜绝推测性的抽象、过早优化与"以防万一"的功能；复杂度必须具有明确且可验证的理由（性能基准、安全需求或既有约束），无法给出理由的复杂度一律拒绝；优先采用标准库与成熟依赖，避免重复造轮子；代码应易于阅读、删除和重构，而非炫技。

### II. 测试先行（不可协商）
<!-- TDD: Red-Green-Refactor -->
任何功能或缺陷修复都必须以测试先行驱动实现：先编写测试并获得对预期行为的确认 → 运行测试确认失败（Red）→ 以最小实现使测试通过（Green）→ 重构；禁止先写实现再补测试；测试必须覆盖公开行为（含边界与失败路径），而非实现细节；未通过测试的代码不得合入。

### III. API 兼容性
<!-- Breaking changes are governed, not accidental -->
所有对外暴露的 API（HTTP 接口、库函数、事件/消息格式、配置与持久化数据格式）在演进时必须默认保持向后兼容；破坏性变更是受控行为：必须先在计划阶段显式声明影响面（调用方、数据迁移、废弃周期），并获得明确批准后才能实施；新增字段应可选，移除或改义需提供过渡期与迁移说明；版本变更遵循语义化版本（MAJOR.MINOR.PATCH）。

### IV. 安全审查
<!-- Permissions & sensitive data -->
凡涉及权限、鉴权、个人数据或任何敏感信息（凭据、通知内容、用户标识等）的功能，必须在规格与计划阶段包含显式的安全审查章节：明确信任边界、最小权限原则、输入校验、敏感数据的存储/传输/日志脱敏与销毁策略；未完成安全审查的此类功能不得进入实现阶段；发现的安全问题为阻塞级缺陷。

### V. 代码审查把关
<!-- No self-merge -->
所有 PR 必须通过至少一名非作者的代码审查方可合入；审查须验证宪法各原则的合规性（简单性、测试先行、兼容性、安全性、双语文档格式）；禁止跳过审查流程，任何"紧急合入"必须事后补审并留档说明。

### VI. 中英双语标题（SDLC 文档格式）
<!-- Bilingual headings: English/中文 -->
所有由 Spec Kit 生成的 SDLC 流程 Markdown 文件（spec、plan、tasks、checklist 及其后续演进产物）中，各级标题——文档大标题（#）、章节标题（##）、模块小标题（### 及以下）——必须采用"英文/中文"双语格式，英文在前、中文在后，以斜杠分隔，例如：`# User Authentication/用户认证`、`## Technical Approach/技术方案`、`### name/姓名`；正文内容语言不受本条限制；标题双语在文档内保持术语一致（同一概念全文使用同一译法）；不符合双语格式的文件不得通过阶段审查门。

## 安全与数据保护要求

- 涉及权限与敏感数据的功能，其规格必须列出：数据类型、访问主体、授权模型、失效与撤销机制。
- 敏感信息不得写入日志、错误信息或测试固件；测试中使用虚构数据。
- 密钥与凭据一律通过环境/安全配置注入，禁止硬编码或提交入库。

## 开发工作流与质量关卡

- 规格 → 计划 → 任务 → 实现 的 SDD 流程依次推进，每个阶段经过人工审查门。
- 计划阶段必须核对：兼容性影响评估、安全审查（如适用）、测试策略。
- 合入门槛：全部测试通过、安全审查完成（如适用）、代码审查批准、宪法合规自查通过。

## Governance

- 本宪法是项目所有实践与决策的最高依据；规格、计划、任务与实现如与本宪法冲突，以宪法为准。
- 修订宪法必须：书面记录修订理由与影响、更新版本号与日期、并为既有不合规项提供迁移计划。
- 团队成员无法裁决合规争议时，保守（更严格）的一方优先。
